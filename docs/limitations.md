# Limitations & honest scope

This is a portfolio-scale prototype, not a GA product. Everything below is a deliberate, bounded decision — the point is that the boundaries are stated, not hidden.

## Authorization coverage is a documented subset

The engine evaluates identity policies (allow/deny), resource policies, trust-assume chains, nested group membership (depth ≤ 5), OAuth consent scopes, and three condition keys (`ip_in`, `time_window`, `asn_type_in`) with AWS-style deny-overrides-allow. It does **not** model:

- Entra Conditional Access policies (session controls, device-compliance gates, sign-in risk as evaluated by Entra ID Protection)
- Azure RBAC inheritance/ABAC attribute conditions, Azure deny-assignments, or PIM just-in-time activation semantics
- AWS permission boundaries, SCPs, or session policies
- Just-in-time / eligible-vs-active role assignment (D5 sees an assignment event; it does not model eligibility pools)

Conditions unknown to the evaluator **fail closed** (they block the route rather than being ignored), so coverage gaps understate access rather than overstate it — the safe direction for a security tool, but still a gap.

## Detection is batch-window, not streaming

Detectors see an evaluation batch (a scenario file or time-boxed window), and "never seen before" is evaluated within that batch. In a streaming deployment the database would supply history; here the batch is the history. First-batch-after-provisioning behavior is a documented false-positive source in every alert's `false_positive_notes`.

## Scoring weights are engineering judgment

signal/access/blast weights (55/30/15 split, 12 points per reachable sensitive resource, confidence-0.6 threshold) are reasoned, documented, and deterministic — but they are **not calibrated against real incident data**. The model is useful for triage ranking; it is not a research result.

## Auth, response, and infrastructure are demo-grade

- **Auth**: static bearer tokens from `SPECTER_TOKENS`. No OIDC, no TLS termination, no rate limiting, no secrets management. The tested claim is the RBAC matrix (401/403), not production identity.
- **Response actions** write an audit row and flip a local flag; they never contact a tenant. Real response needs approval gates, scoped credentials, and dry-run — deliberately out of scope.
- **Storage**: SQLite by default; the schema is portable to Postgres via `DATABASE_URL`, but CI only exercises SQLite. No migrations framework (tables are created via `create_all`); schema changes are drop-and-recreate at this stage.
- **Scale**: the load test measures *ingestion* throughput on one node (10k–1M events). Query-path fan-out (the identities endpoint evaluates the graph per identity) is measured at demo scale (29 identities, p95 ≈ 13 ms) — it is not a distributed-systems benchmark.

## Evaluation data is synthetic

Northstar Health is generated, seed-pinned, and fictional (`datasets/provenance.json`). Detection recall/FP numbers are measured against those labeled fixtures — they demonstrate the harness works, not production accuracy. City coordinates are coarse centroids; real GeoIP quality is one of the documented FP rules.

## Frontend has no automated browser tests

The SPA is exercised by the API contract tests plus the screenshots in `demo/`, which are regenerated by hand. The XSS discipline (every API-derived value passes `esc()`) is an enforced code invariant, not a runtime CSP. A Playwright pass would be the next quality increment.
